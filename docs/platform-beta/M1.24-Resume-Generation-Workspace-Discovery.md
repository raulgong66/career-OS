# M1.24 Resume Generation Workspace — Discovery Document

**Status:** DRAFT — Architectural Discovery
**Milestone:** M1.24
**Depends on:** M1.21 Artifact Workspace, M1.22 CSKS Foundation, M1.23 CSKS Developer Experience

---

## Executive Summary

This discovery document analyzes the existing Resume Generation subsystem and proposes its evolution into a **Resume Generation Workspace** — a richer, more integrated experience that preserves all existing generators, templates, artifact models, REST endpoints, CLI commands, and UI while adding deterministic profile quality analysis, a unified recommendation workflow, and a cohesive end-to-end user journey from profile selection to export.

**Key findings:**

1. **Resume Generation already works** — 8 generators (4 Markdown + 4 DOCX), 2 templates (`standard_cv`, `standard_interest_letter`), full artifact lifecycle (create → preview → export .md/.docx), JD-aware tailored generation, and a working Tailoring page with 4 resolvable profile-quality rules.

2. **Profile Quality rules exist but are fragmented** — 8 profile-quality rules in `recommendation_rules.py` (structural profile health) and 6 element-type ADD recommendations in `CVOptimizer` (CV gap analysis) operate independently with no unified pipeline, shared metrics, or cross-consumer reuse.

3. **Resolution workflow exists for 4 rules** — `resolution.py` applies deterministic edits to the canonical profile for `ProjectWithoutSkillsRule`, `ExperienceNoTechnologiesRule`, `SkillWithoutExperienceRule`, `NoMeasurableAchievementRule`, marks affected artifacts stale, and re-triggers analysis. This is currently only reachable from Tailoring.

4. **No deterministic "Resume Health" score exists** — The system produces rule-level findings and optimization summaries but no aggregate, deterministic, citable health metric for the profile or artifact.

5. **Integration points are well-defined but under-used** — The Canonical Profile schema (18 entity types, ID-based cross-references), `ExportContract` (unified generation input), `ReasoningFindings` (8 fields from Reasoning Engine), and `Artifact` model (status current/stale, sourceRefs) form a clean architecture that Resume Generation Workspace should fully leverage.

6. **Architecture boundaries are enforced** — ADR-004 requires Core/Module/App separation. Resume Generation is a Module consuming Core (generators, reasoning, schemas, acquisition). The Workspace evolution must not violate this.

## 3. Proposed Evolution: Current → Workspace

### 3.1 Why Evolve, Not Redesign?

| Evolution Principle | Rationale |
|---|---|
| **Preserve all working code** | 8 generators, 2 templates, 31 rules, 9 REST endpoints, 2 UI pages, acquisition pipeline — all production-ready |
| **Extend, don't replace** | Architecture boundaries (ADR-004) require Modules to consume Core, not duplicate it |
| **Reuse existing integration points** | ExportContract, ReasoningFindings, Artifact model, Profile schema, Resolution Engine already cleanly defined |
| **Incremental value delivery** | Each new capability (Profile Quality Engine, Resume Health, unified recommendations) adds value without breaking existing flows |
| **No schema changes** | Profile schema already supports all needed fields (artifacts.sourceRefs, extensions, evidence) |
| **No API breaking changes** | Existing endpoints remain; new endpoints are additive |

### 3.2 Evolution Delta

| Current State | Workspace Evolution |
|---|---|
| Artifact Workspace = creation + export | **Workspace = Dashboard + Creation + Preview + Improvement Queue + Export** |
| Profile quality rules only in Tailoring | **Unified Profile Quality Engine** consumed by Workspace, Tailoring, CSKS, future Analytics |
| 4 resolvable rules only in Tailoring | **Resolution Workflow** accessible from Workspace, Tailoring, CLI, API |
| No Resume Health metric | **Deterministic Resume Health Score** (profile + artifact levels) with citations |
| Two separate recommendation UIs | **Unified Recommendation Component** (profile-quality + optimization) |
| Stale artifacts = manual regenerate | **Staleness Detection + Auto-Refresh + Diff View** |
| No artifact preview before create | **Template Preview** (render with sample data or current profile subset) |
| No version history | **Artifact Versioning** (immutable history per artifact ID) |

## 4. Resume Workspace Vision

### 4.1 Vision Statement

> The **Resume Generation Workspace** is a deterministic, profile-centric environment where users:
> - See an immediate **Resume Health dashboard** for their canonical profile and each artifact
> - Browse a prioritized **Improvement Queue** of deterministic, citable findings
> - Resolve issues inline via the **shared Resolution Workflow** (mutating the canonical profile)
> - Preview artifacts before creation with **Template Preview**
> - Generate, compare versions, and export with confidence that every recommendation is traceable to evidence in their profile

### 4.2 Workspace Capabilities (New)

| Capability | Description | Reuses |
|---|---|---|
| **Profile Quality Dashboard** | Aggregate Resume Health score + breakdown by dimension | Reasoning Engine, CVOptimizer |
| **Improvement Queue** | Prioritized, filterable list of all findings (profile-quality + optimization) with resolution actions | Reasoning Engine results, CVOptimizer recommendations, Resolution Engine |
| **Template Preview** | Render any template with current profile data (or subset) before creating artifact | Generators, ExportContractBuilder, EvidenceSelector |
| **Artifact Version History** | Immutable snapshots per artifact ID; diff between versions | Profile Repository, Artifact model extensions |
| **Staleness Auto-Detection** | Background job or on-access check: if any sourceRef element mutated → mark stale + notify | Resolution Engine's `_mark_affected_artifacts_stale()` logic |
| **Unified Recommendation Card** | Single component rendering profile-quality findings + optimization recommendations | TailoringPage rendering logic, API DTO shapes |
| **Resolution Panel** | Reusable panel for the 4 resolvable rules (skills, technologies, achievements, project links) | resolution.py apply_resolution(), TailoringPage resolution panel |

### 4.3 Preview Contract (Strict, Read-Only)

> **M1.24.0 Architectural Clarification:**
> **Preview is render-only. It is the fastest path in the Resume Workspace and must never have side effects.**

The Template Preview endpoint and the `ArtifactTemplate.preview(profile)` protocol method MUST obey the following guarantees:

| Property | Required Behavior |
|---|---|
| **Read-only** | Preview MUST NOT write to any persistent storage |
| **No side effects** | No I/O beyond returning rendered markdown/bytes |
| **No artifact persistence** | Preview MUST NOT create an artifact record, even temporarily |
| **No profile mutation** | Preview MUST NOT modify the Canonical Profile |
| **No exports** | Preview MUST NOT trigger DOCX export, file download, or external services |
| **No version creation** | Preview MUST NOT create an artifact version entry |
| **No tailoring context** | Preview MUST NOT require or accept a Job Description |
| **No background processing** | Preview is synchronous; no queues, workers, or async jobs |
| **Deterministic** | Same profile + same template → identical preview output |
| **Fastest path** | Preview MUST skip reasoning re-run, JD processing, and version writes |

Implementation constraints:

- Preview invokes the existing Generator registry via `ExportContractBuilder` with `validate=False` and `reasoning=None`.
- Preview reuses the existing `EvidenceSelector` to filter sources; it does **not** re-implement source selection.
- Preview results may be cached per `(template_id, profile_version)` tuple; cache is invalidated when the profile is mutated by Resolution.
- Preview **cannot** be used to satisfy an export request. An explicit Create + Generate + Export flow is required to produce an artifact.

### 4.4 Artifact Versioning Scope (Artifacts Only — Profile Stays Unversioned)

> **M1.24.0 Architectural Clarification:**
> **Versioning belongs to generated artifacts and Resume Workspace history. The Canonical Profile remains the single source of truth and is NOT versioned by this milestone.**

| Concern | Owner |
|---|---|
| **Canonical Profile history** | Profile Repository (`careeros.profile_repository`) — staging/canonical/archived states; **not modified by versioning** |
| **Artifact version history** | Artifact record, under `extensions._versions` — created by Workspace only |
| **Workspace history (preview cache, improvement-queue cache)** | Workspace-local cache — invalidates on profile mutation |

Explicit guarantees:

1. **ProfileQualityEngine MUST NOT version profiles.** It reads the canonical profile and emits a report; it does not write history.
2. **Artifact history MUST NOT mutate Canonical Profile history.** When an artifact is regenerated, the new version entry references the existing `sourceRefs`; it does not snapshot the profile.
3. **Profile mutation flow remains Resolution → Profile Repository.** Resolution continues to mutate the canonical profile in place; the Workspace observes the change via invalidation, not via per-version diffs.
4. **Preview cache invalidation hooks into Resolution Engine's existing staleness signal** (`_mark_affected_artifacts_stale()` and the equivalent profile-mutation hook added by this milestone). No new version mechanism is introduced for profiles.
5. **CSKS query layer remains the authoritative surface for "what changed in my profile?"** Versioning queries apply to artifacts only.

Diagram (after clarification):

```
Canonical Profile (single source of truth, NOT versioned by M1.24)
       │
       ├──► Profile Repository: writes only on Resolution or Acquisition
       │
       ▼
Workspace observes canonical profile state
       │
       ├──► Artifact A (in profile.artifacts[])
       │       └── extensions._versions = [v1, v2, v3]   ← workspace-managed
       │
       ├──► Artifact B (in profile.artifacts[])
       │       └── extensions._versions = [v1, v2]       ← workspace-managed
       │
       └──► Preview cache (workspace-local)
               └── invalidated by Resolution Engine's profile-mutation signal
```

Profile history remains the responsibility of the Profile Repository state machine (`staging` → `canonical` → `archived`). M1.24 adds no new profile-versioning layer.

## 5. Profile Quality Engine Assessment

> **M1.24.0 Architectural Clarification (added after Copilot review, PASS WITH RECOMMENDATIONS):**
> **ProfileQualityEngine is a facade over existing deterministic platform capabilities. It introduces orchestration, not new business rules.**
> It owns **orchestration only** and **must not become another reasoning engine**.
> It reuses — never replaces — the following existing Core capabilities:
>
> - **Reasoning Engine** (`careeros.reasoning`) — registers and executes the 8 profile-quality rules
> - **Resolution Engine** (`careeros.resolution`) — exposes resolution actions for the 4 resolvable rules
> - **EvidenceSelector** (`careeros.evidence_selector`) — selects evidence by target context when scoring
> - **ExportContract** (`careeros.export_contract`) — the unified input contract for generators used by Preview
> - **CSKS** (`careeros.csks`) — surfaces the same findings via the developer-experience query layer
>
> ProfileQualityEngine **must not**:
> - Re-implement any rule already present in `recommendation_rules.py`
> - Re-implement any resolution action already present in `resolution.py`
> - Maintain its own copy of the canonical Profile, knowledge graph, or scoring heuristics
> - Introduce a second rule registry or a parallel engine pipeline

### 5.0 Scope (Strict, Profile-Centric)

ProfileQualityEngine operates **only** on the **Canonical Profile** (the single source of truth, per ADR-004 and `careeros.profile_repository`).

ProfileQualityEngine **must**:
- Evaluate canonical profiles (read-only on the profile dict)
- Generate deterministic findings via the existing Reasoning Engine
- Generate deterministic recommendations via the existing Resolution Engine for resolvable findings
- Generate profile health scores by composing the 8 deterministic dimension calculators over reasoning findings

ProfileQualityEngine **must not**:
- Depend on Tailoring, the Tailoring UI, or any Tailoring-specific DTO
- Depend on Job Descriptions or any CV-Optimizer-internal scoring
- Depend on Interview Intelligence or its evaluation domain
- Import any consumer (Workspace, Tailoring, Interview, CSKS, CLI) — consumers depend on ProfileQualityEngine, never the reverse
- Carry JD, artifact, or session context

Tailoring and other workspaces **may consume** `ProfileQualityEngine` results. ProfileQualityEngine **remains independent** of those consumers.

### 5.2 Should It Be a Shared Platform Capability?

**Yes, with conditions:**

| Consumer | Value | Requirements |
|---|---|---|
| **Resume Generation Workspace** | Dashboard health score, improvement queue | Full report + health score + citations |
| **Tailoring** | Pre-filter profile recommendations before JD optimization | Full report; already runs `POST /analyze` |
| **Interview Intelligence** | Surface skill gaps, missing evidence before interview prep | Skill/evidence findings, core competencies |
| **CSKS** | Answer "How healthy is this profile?" via query engine | Structured query results with citations |
| **Future Analytics** | Trend health over time, compare profiles | Stable report schema, deterministic scoring |

**Conditions for sharing:**

1. **Single execution, multiple consumers** — Engine runs once per profile; consumers read cached report. Not re-executed per consumer.
2. **Deterministic, no AI** — All rules are pure functions on the profile dict. No LLM, no embeddings, no fuzzy matching.
3. **Citable outputs** — Every finding includes evidence references (evidenceRefs, element IDs) for auditability.
4. **Extensible rule registry** — New rules register deterministically; existing rules never change behavior without version bump.
5. **Profile-only input** — Engine operates on canonical profile dict. No artifact/JD context (that's CVOptimizer's role).
6. **Facade, not engine** — ProfileQualityEngine does not own rule logic, scoring algorithms, or graph traversal. It composes existing capabilities.
7. **No consumer dependencies** — Engine never imports Tailoring, CVOptimizer, Interview Intelligence, or any consumer module.

### 5.3 Relationship to CVOptimizer (Clear Separation)

| Aspect | Profile Quality Engine (facade) | CVOptimizer |
|---|---|---|
| **Role** | Orchestrates existing rule execution + aggregates scores | Performs artifact-vs-JD gap analysis |
| **Input** | Canonical Profile only | Canonical Profile + Artifact + Job Description |
| **Question** | "What is wrong with this profile?" | "What is missing from this CV for this job?" |
| **Output** | Reasoning findings + health score | ADD recommendations with JD-weighted scores |
| **Owns logic?** | No — reuses Reasoning + Resolution | Yes — owns JD concept extraction and scoring |
| **Deterministic** | Yes | Yes (but JD-dependent) |
| **Reusability** | Platform-wide (no JD needed) | Tailoring-specific (requires JD) |
| **Rules** | Reuses 8 existing profile-quality rules in `recommendation_rules.py` | 6 element types + JD concept extraction |

**They are complementary, not redundant.** The Workspace may run both:
1. ProfileQualityEngine → health score + structural improvement queue (always)
2. CVOptimizer (when JD provided, in Tailoring) → targeted ADD recommendations

The dependency direction is **strict**: Tailoring may call ProfileQualityEngine, then call CVOptimizer. Neither engine depends on the other.

## 6. Resume Health Proposal

### 6.1 Definition

**Resume Health** is a deterministic, citable score (0–100) representing the structural completeness and evidence quality of a **Canonical Profile** or a specific **Artifact**.

### 6.2 Metrics (Deterministic Calculations)

#### Profile-Level Health (Profile Quality Engine)

| Dimension | Weight | Calculation | Evidence |
|---|---|---|---|
| **Achievement Measurability** | 20% | % of experiences with ≥1 measurable achievement (metrics OR business outcome words OR numbers) | `NoMeasurableAchievementRule` findings |
| **Skill Evidence Coverage** | 20% | % of skills with ≥1 experience/achievement evidence link | `SkillWithoutExperienceRule` findings |
| **Technology Presence** | 15% | % of experiences mentioning ≥1 recognized technology keyword | `ExperienceNoTechnologiesRule` findings |
| **Summary Quality** | 10% | 1 if professional summary exists, non-generic, ≥40 chars, has metrics/tech; else 0 | `GenericSummaryRule` findings |
| **Skill Deduplication** | 10% | 1 if 0 duplicate skills after normalization; else 1 - (dup_count / total_skills) | `DuplicateSkillsRule` findings |
| **Business Outcome Language** | 10% | % of achievements with business outcome words | `MissingBusinessOutcomeRule` findings |
| **Certification Utilization** | 10% | % of certifications referenced in experience or with evidence | `CertificationUnreferencedRule` findings |
| **Project Skill Linkage** | 5% | % of projects with ≥1 skillRef OR experienceRef | `ProjectWithoutSkillsRule` findings |

**Aggregate Formula:** `health_score = Σ(dimension_weight × dimension_score) × 100` → integer 0–100

Each dimension score is a rational number computable directly from the profile dict — no AI, no randomness.

#### Artifact-Level Health (CV-Specific)

| Metric | Calculation |
|---|---|
| **Source Coverage** | % of artifact's `sourceRefs` that resolve to valid profile elements |
| **Staleness** | 0 if all sourceRefs current; 1 if any source element mutated since artifact creation |
| **Profile Alignment** | % of profile's high-priority elements (per health dimensions) present in artifact |

### 6.3 User Value

| User Need | How Resume Health Addresses |
|---|---|
| "Is my profile ready?" | Single 0–100 score with dimension breakdown |
| "What should I fix first?" | Improvement Queue sorted by dimension weight × finding priority |
| "Why this score?" | Every dimension cites specific evidence (experience IDs, skill IDs, achievement IDs) |
| "Will this help me get interviews?" | Health dimensions map to recruiter impact (measurable achievements, skill evidence, technologies) |
| "How do I compare profiles?" | Deterministic score enables comparison across profiles |

### 6.4 Additional Deterministic Analyses (Recommended)

| Analysis | Description | Implementation |
|---|---|---|
| **Consistency Check** | Cross-entity validation: dates don't overlap incorrectly, organizationRefs resolve, skill categories consistent | New rule in Profile Quality Engine |
| **Freshness Index** | Days since last profile update; % of experiences with `isCurrent=true` but end date in past | Computed from dateRange fields |
| **Evidence Density** | Ratio of evidence items to claims (skills + experiences + achievements) | `len(evidence) / (len(skills)+len(experiences)+len(achievements))` |
| **Target Context Alignment** | For a given targetContext, % of emphasis areas covered by profile elements | Match `targetContext.emphasis[]` against skill/experience/project text |
| **Readability Score** | Flesch-Kincaid on professional summaries + experience scopes | Deterministic text analysis |

### 7.2 Problems

| Problem | Impact |
|---|---|
| **Duplicated recommendation rendering logic** | Tailoring has custom rendering for two different recommendation shapes |
| **Inconsistent action sets** | Profile recs: Review/Dismiss/Resolve/GoTo; Optimization recs: no actions |
| **No shared component** | Cannot reuse in Workspace, CSKS, CLI, future pages |
| **Resolution only in Tailoring** | 4 resolvable rules inaccessible from Workspace |
| **No unified "Improvement Queue" concept** | User cannot see all pending improvements in one place |

### 7.3 Proposed Unified Recommendation Model

**Single Recommendation Shape (internal):**

```python
class UnifiedRecommendation:
    id: str                          # stable ID
    source: "profile_quality" | "optimization"  # provenance
    rule_id: str                     # e.g., "recommendation_add_measurable_achievement"
    element_id: str                  # profile element ID
    element_type: str                # "experience" | "skill" | "project" | ...
    title: str                       # human-readable title
    reason: str                      # why this matters
    suggested_action: str            # deterministic action text
    resolution_type: "auto" | "guided" | "none"  # can resolution engine fix it?
    evidence_refs: list[str]         # evidence IDs backing this
    priority: "high" | "medium" | "low"
    estimated_impact: "high" | "medium" | "low"
    confidence: "high" | "medium" | "low"
    # Optimization-specific (optional):
    jd_match_score: float | None
    context_match_score: float | None
```

**Mapping:**

| Current Source | Maps To |
|---|---|
| `ReasoningResult` (profile-quality) | `source="profile_quality"`, `resolution_type="auto"` for 4 rules, `"guided"` for others |
| `OptimizationResult.Recommendation` | `source="optimization"`, `resolution_type="none"` (ADD only) |

**Unified API Response:**

```json
{
  "profile_quality_report": { ... },
  "recommendations": [ UnifiedRecommendation ... ],
  "optimization_result": { ... }  // only when JD provided
}
```

**Workspace UI consumes single `recommendations` array** — renders with appropriate actions based on `resolution_type`.

## 8. User Workflow

### 8.1 Ideal End-to-End Workflow

```
1. USER OPENS RESUME GENERATION WORKSPACE (/artifacts)
   │
   ├──► Loads Profile Quality Report for selected profile
   │       • Health Score: 72/100
   │       • Dimensions: Achievements 60%, Skills 85%, Tech 70%, ...
   │       • 8 findings in Improvement Queue
   │
   ▼
2. USER REVIEWS IMPROVEMENT QUEUE (left panel)
   │
   ├──► Filterable by: dimension, priority, resolvability
   ├──► Each item shows: title, reason, element preview, actions
   │
   ▼
3. USER RESOLVES HIGH-PRIORITY ITEMS
   │
   ├──► Clicks "Add Measurable Achievement" for Experience E3
   │       → Opens Resolution Panel (guided)
   │       → User writes achievement statement, links skills
   │       → Clicks "Apply" → POST /profiles/{id}/resolve
   │       → Profile mutated, affected artifacts marked stale
   │       → Queue refreshes; health score updates to 78
   │
   ├──► Clicks "Add Skills to Project P1"
   │       → Opens Resolution Panel (auto)
   │       → User selects skills from checkbox list
   │       → Applies; ProjectWithoutSkillsRule finding clears
   │
   ▼
4. USER PREVIEWS TEMPLATE BEFORE CREATION
   │
   ├──► Hovers "Standard CV" template → "Preview" button
   │       → Renders markdown with current profile data (fast, cached)
   │       → Shows estimated source count, artifact health prediction
   │
   ▼
5. USER CREATES ARTIFACT
   │
   ├──► Clicks "Create" on Standard CV
   │       → POST /profiles/{id}/artifacts {template: "standard_cv"}
   │       → Artifact appears in list with status "current"
   │
   ▼
6. USER PREVIEWS & EXPORTS
   │
   ├──► Selects artifact → POST /generate/artifact {format: markdown}
   │       → Preview renders with custom markdown renderer
   │       → "Export .md" / "Export .docx" buttons
   │
   ▼
7. (OPTIONAL) USER TAILORS FOR SPECIFIC JOB
   │
   ├──► Clicks "Tailor for Job" → navigates to /tailoring with profile pre-selected
   │       → Pastes JD → Generate → gets optimization recommendations
   │       → Applies ADD recommendations → regenerates
   │       → Returns to Workspace; artifact updated
   │
   ▼
8. USER EXPORTS FINAL RESUME
   │
   └──► Downloads .docx or .md → ready to submit
```

### 8.2 Key Workflow Principles

| Principle | Implementation |
|---|---|
| **Profile-first** | Health score and improvement queue derive from canonical profile, not artifact |
| **Resolution mutates profile** | Fixing root cause (profile) benefits all artifacts and consumers |
| **Staleness is visible** | Artifact list shows `current`/`stale` with auto-refresh option |
| **Preview before commit** | Template preview uses same generator pipeline (fast path) |
| **Tailoring is a mode, not a separate silo** | Workspace → Tailoring → back to Workspace with updated artifact |
| **Every action is traceable** | Resolution creates audit entry; health score cites evidence |

## 10. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| **Duplicated logic between Profile Quality Engine and CVOptimizer** | High | Clear separation: Engine = profile-only structural; Optimizer = artifact+JD gap analysis. Shared utilities (evidence verification) extracted to `careeros/quality_utils.py`. |
| **Duplicated recommendations** | High | UnifiedRecommendation model normalizes both sources; UI consumes single array; deduplication by `(rule_id, element_id)` at API layer. |
| **Coupling Workspace ↔ Tailoring** | Medium | Tailoring remains a separate page; Workspace links to it with profile pre-selected. Shared recommendation component avoids UI coupling. |
| **Unnecessary generator proliferation** | Low | No new generators. Template Preview reuses existing 8 generators. |
| **Conflicting workflows (profile mutation vs. artifact tailoring)** | Medium | Resolution mutates canonical profile (affects all artifacts). Tailoring creates tailored artifact copy (affects one artifact). Both valid; user chooses. Document clearly in UI. |
| **Stale artifact explosion** | Medium | `_mark_affected_artifacts_stale()` already exists. Workspace adds staleness badge + one-click regenerate. Background job optional (M1.25+). |
| **Performance: Profile Quality Engine on every load** | Low | Report cached per `profile_version`. Invalidated on profile mutation (resolution, acquisition). Typical profile < 50KB; 31 rules < 50ms. |
| **Frontend component debt** | Medium | No shared components today. Workspace introduces first shared components (`RecommendationCard`, `ResolutionPanel`, `HealthScore`, `ArtifactPreview`). Incremental extraction from TailoringPage. |
| **Profile mutation audit trail** | Low | Resolution already deep-copies `before` snapshot. Extend to persist audit log in `extensions._resolution_history` array. |
