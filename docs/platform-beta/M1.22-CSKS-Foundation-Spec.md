# M1.22 — CSKS Foundation Specification

## Objective

Design and implement the **CareerOS Self-Knowledge System (CSKS)** as an internal knowledge and answering system for CareerOS itself. CSKS enables accurate, deterministic answers about CareerOS architecture, modules, components, code organization, APIs, workflows, ADR decisions, data models, tests, operational procedures, and milestone history.

This milestone delivers the CSKS foundation: specification, knowledge model, architecture decision, core extractor, graph builder, query engine, CLI command, API endpoint, and comprehensive tests. **No LLM integration in this milestone** — CSKS is purely deterministic, aligned with the Manifesto principle "Reasoning Before Generation."

**Key Architectural Decision**: CSKS reuses the existing `careeros.knowledge.KnowledgeGraph` as its graph engine. CSKS does NOT create a parallel graph implementation. CSKS entities are stored as `GraphNode`/`GraphEdge` instances in the existing `KnowledgeGraph` class. CSKS is a knowledge domain layer that populates and queries the existing graph infrastructure.

---

## User Journey

1. A developer or AI agent asks: *"What domains depend on Profile Management?"*
2. CSKS extracts structured knowledge from source code, documentation, schemas, and configuration.
3. CSKS populates the existing `careeros.knowledge.KnowledgeGraph` with CSKS entities as `GraphNode`/`GraphEdge` instances.
4. CSKS Query Engine traverses the graph and returns: `"Knowledge Graph, Reasoning, Resolution, Export Contract, Generation, Acquisition, CV Optimization depend on Profile Management"` with source citations.
5. The same query works via CLI (`careeros csks query "..."`) and REST API (`GET /csks/query?q=...`).

## Functional Requirements

### 3.1 Knowledge Extraction
- **Source code**: Extract domains, modules, classes, functions, dependencies (Python AST), TypeScript/React components (TS AST), configuration keys
- **Documentation**: Extract ADRs (id, status, summary), milestone specs (id, status, acceptance criteria), architecture docs (domain map, data flows, interfaces)
- **Schemas**: Extract all 18 JSON Schema entities with fields, types, constraints
- **Tests**: Map test files to components they exercise
- **Configuration**: Extract keys from pyproject.toml, vite.config.ts, .env.example
- **Git history**: Extract milestone tags, release tags, commit metadata

### 3.2 Knowledge Graph Construction
- **Reuses** `careeros.knowledge.KnowledgeGraph` as the graph engine — no parallel graph implementation
- CSKS entities are stored as `GraphNode` instances with `type` in `{"domain", "component", "api_endpoint", "cli_command", "rule", "generator", "schema", "test", "adr", "milestone", "configuration", "principle", "dataflow", "dependency"}`
- CSKS relationships are stored as `GraphEdge` instances with `type` in `{"contains", "depends_on", "produces", "consumes", "implements", "validates_against", "flows_to", "references", "specifies", "tags", "configures"}`
- Graph is immutable after construction; deterministic (same sources → same graph)
- CSKS defines a `KnowledgeExtractor` protocol for source-specific extraction

### 3.3 Query Engine
Support these query patterns:
- **Entity lookup**: `"What is the TotalYearsExperienceRule?"` → rule definition + inputs/outputs + source file
- **Type filter**: `"List all domains"` → 8 domains with descriptions
- **Dependency traversal**: `"What depends on Profile Management?"` → reverse dependency list with paths
- **Data flow path**: `"Data flow for artifact generation"` → Profile → Load → Validate → KG → Reasoning → Contract → Generate
- **Capability check**: `"Does CareerOS support PDF generation?"` → No (from capabilities table)
- **Status query**: `"M1.21 status"` → Completed (tag m1.21-artifact-workspace)
- **Impact analysis**: `"What breaks if I change ProfileLoader?"` → dependent components

### 3.4 Interfaces
- **CLI**: `careeros csks query "natural language or structured query"`
- **REST API**: `GET /csks/query?q=...` returning JSON with answer + citations
- **Answer format**: Structured response with `answer`, `citations` (file:line), `confidence` (1.0 for deterministic)

### 3.5 Incremental Indexing (M1.23 scope, design here)
- On commit, git diff identifies changed files
- Only re-extract and re-index affected entities
- Index stored as file-based, git-aware artifacts

## Backend / Domain Requirements

- Implement CSKS as a new Core domain under `careeros/csks/`
- **Extractor**: Static analysis of Python (AST), TypeScript (optional), Markdown, JSON, YAML, TOML
- **Builder**: Populates `careeros.knowledge.KnowledgeGraph` via `KnowledgeGraphBuilder` pattern
- **Query Engine**: Graph traversal (DFS/BFS), faceted filters, path finding (Dijkstra for weighted paths)
- **Indexer**: File-based incremental index with git diff awareness (M1.23)
- **Models**: Frozen dataclasses for all CSKS entities and relationships (for type-safe extraction output)
- **No LLM**: Pure deterministic extraction and query
- **Reuse**: 
  - `careeros.knowledge.KnowledgeGraph` as graph engine
  - `careeros.knowledge.KnowledgeGraphBuilder` pattern for graph construction
  - `careeros.reasoning.registry.RuleRegistry.execution_order()` for topological sort
  - `careeros.schema_loader.SchemaLoader` for schema discovery patterns

## API Requirements

| Method | Path | Purpose |
|---|---|---|
| GET | `/csks/query?q={question}` | Execute query, return structured answer |
| GET | `/csks/entity/{entity_id}` | Get entity details with relationships |
| GET | `/csks/search?type={type}&domain={domain}` | Faceted search |
| POST | `/csks/index` | Trigger full re-index (admin) |
| GET | `/csks/status` | Index status (entity count, last updated, stale files) |

**Response format**:
```json
{
  "answer": "Knowledge Graph, Reasoning, Resolution, Export Contract, Generation, Acquisition, CV Optimization depend on Profile Management",
  "citations": [
    {"file": "docs/architecture/02-domain-map.md", "line": 90, "text": "KG --> Profile"},
    {"file": "careeros/reasoning/engine.py", "line": 29, "text": "from careeros.knowledge import KnowledgeGraphBuilder"}
  ],
  "confidence": 1.0,
  "entities_found": 7,
  "query_time_ms": 12
}
```

## Architecture Constraints

- **Preserve Canonical Profile** as single source of career data — CSKS is meta-knowledge about CareerOS, not career data
- **CSKS is Core** — deterministic, module-neutral, no LLM dependencies
- **Dependency flow**: Core → CSKS (CSKS is a Core domain, not a module)
- **No lateral bypassing**: CSKS reads sources directly; does not call API/CLI
- **Deterministic only**: Same sources → same graph → same answers
- **Citations mandatory**: Every answer traces to source file:line
- **No AI provider dependencies** in this milestone
- **No parallel graph** — CSKS uses existing `careeros.knowledge.KnowledgeGraph`

## Milestone Summary

M1.22 delivers the **CSKS Foundation**: a deterministic, graph-based internal knowledge system for CareerOS. It enables developers and AI agents to ask structural questions about the codebase, architecture, APIs, and processes — and receive accurate, cited answers. This is the first step toward making CareerOS self-documenting and self-navigable, directly supporting the Manifesto principles of explainability, deterministic reasoning, and knowledge as a permanent asset.

**Key Architectural Principle**: CSKS is a knowledge domain layer that **reuses** the existing `careeros.knowledge.KnowledgeGraph` as its graph engine. No parallel graph implementation is created. CSKS entities are stored as `GraphNode`/`GraphEdge` in the existing graph infrastructure.
