# M1.23 — CSKS Developer Experience & Semantic Query Layer

## Objective

Build an interpretation and presentation layer **on top of** the frozen M1.22 CSKS
foundation (KnowledgeGraph, extractors, builder, indexer, REST endpoints, entity model).
The layer makes CSKS feel like a real developer assistant: a deterministic query grammar
with intent classification, an alias registry for entity resolution, a grouped search
command, rich per-type answer formatting, and helpful "did you mean" suggestions — all
without AI, embeddings, vector search, or fuzzy matching.

Everything in this milestone is **fully deterministic**: the same question always produces
the same answer. Answers are always sourced (file:line citations) and every claim traces
back to the knowledge graph.

**Key Architectural Decision**: M1.23 adds a query-time interpretation layer
(`careeros/csks/grammar.py`, `careeros/csks/aliases.py`, `careeros/csks/search.py`,
`careeros/csks/rich_format.py`). It does **not** replace any frozen component. The
`KnowledgeGraph`, `GraphNode`/`GraphEdge`, extractor architecture, builder architecture,
index storage, existing REST endpoints, and the entity model remain exactly as delivered
in M1.22/M1.22.1.

---

## Scope

1. Replace the current keyword heuristic (`CSKSQueryEngine._classify_query`) with an
   ordered, rule-based **deterministic query grammar** that recognizes the mandated intent
   categories.
2. Add **entity resolution** via an alias registry (entity-type aliases, domain canonical
   names, identifier normalization incl. milestones).
3. Add a grouped **search** capability: `careeros csks search <term>` and the
   `search`/`find` query intent, both returning results grouped by entity type.
4. Add a **rich answer formatter** that renders Components, Domains, ADRs, and Milestones
   as structured, human-readable sections (with citations) instead of raw property dumps.
5. Improve **CLI UX**: replace "Unknown query type." with "I could not classify your
   query." plus deterministic "Did you mean:" suggestions.
6. Add **API parity** for the new capabilities (additive only — existing endpoints and
   response shapes unchanged).
7. Ship `docs/csks/` user documentation with ≥50 example queries.
8. Expand the test suite to cover all new behavior and re-verify the 19 acceptance
   criteria queries.

## Goals

- Every accepted-query pattern in the milestone answers correctly with citations.
- Backward compatibility: all M1.22/M1.22.1 tests keep passing (baseline 836).
- Same question → same answer, always (determinism).
- Answers are self-explanatory: rich, sectioned, and cite `file:line` for every claim.
- `careeros csks search <term>` returns grouped, deduplicated results across all major
  entity types.
- Documentation enables a developer to learn CSKS in minutes and gives ≥50 copy-pasteable
  example queries.

## Non-goals

- **No AI / no embeddings / no vector search / no fuzzy matching.** All matching is
  substring/prefix/exact against normalized identifiers and labels.
- No changes to frozen components: `careeros.knowledge` graph classes, extractor
  architecture, builder architecture, index storage format, existing REST endpoint
  contracts, entity model (`models.py` entity/relationship type sets are untouched;
  `QueryType` literal is extended additively only).
- No new entity types, no new extractors, no re-indexing of sources.
- No incremental indexing (still deferred; `CSKSIndexer.incremental_update` keeps its
  full-rebuild stub behavior).
- No frontend/UI work.
- No persistence beyond the existing `.csks-index/metadata.json`; the interpretation layer
  is computed at query time and is stateless.
- No mutation of the graph at query time; the layer is read-only.

## 4. Query Grammar

The grammar recognizes the following intent categories. Each maps to a
`query_type` value returned by the engine and the API.

| Intent | `query_type` | Example |
|---|---|---|
| Component lookup | `entity_lookup` | `What is ProfileLoader?` |
| Domain lookup | `entity_lookup` | `What is Profile Management?` |
| Listing | `type_filter` | `List domains.` |
| Dependency analysis (who depends on X) | `dependency_traversal` | `What depends on ProfileLoader?` |
| Reverse dependency (what X depends on) | `reverse_dependency` *(new)* | `What does ArtifactGenerator depend on?` |
| Impact analysis | `impact_analysis` | `What breaks if I change ProfileLoader?` |
| Data flow | `data_flow_path` | `How does artifact generation work?` |
| Search | `search` *(new)* | `Search profile.` |
| Capability check | `capability_check` | `Does CareerOS support PDF generation?` |
| Status check | `status_check` | `M1.22 status` |
| Not understood | `unknown` | `potato potato potato` |

`QueryType` in `careeros/csks/models.py` gains two additive members: `reverse_dependency`
and `search`. No existing member is removed or renamed, preserving the API contract.

### Grammar structure

`careeros/csks/grammar.py` defines an ordered list of `IntentRule`s. Each rule has:

- `intent`: the `query_type` it maps to,
- `patterns`: ordered regexes (case-insensitive) that fire the intent,
- `extractor`: a small deterministic function that pulls the target tokens (entity name,
  type noun, milestone number, search term) out of the question,
- `guard`: optional predicates (e.g., "a target token must be present") that suppress the
  intent when the trigger is misleading.

Classification walks rules **first-match-wins** (highest-specificity rules first) and
returns a `ClassifiedIntent(query_type, target, params, hints)`. The `CSKSQueryEngine`
then dispatches to the existing handler for that intent (or a new handler for the two new
intents). This keeps all graph traversal logic in the query engine while moving all
"understanding" into the grammar.

### Trigger examples (normative)

| Intent | Triggers (regex, lowercase) |
|---|---|
| `entity_lookup` | `what is`, `what are`, `who is`, `define`, `describe`, `explain` (without `how`), `tell me about`, `show me` — plus a CamelCase/acronym/capitalized target token, or an ADR/milestone identifier |
| `listing` | `list`, `show all`, `enumerate`, `list all` + a type noun (`domains`, `generators`, `api endpoints`, `rules`, `adrs`, `milestones`, `schemas`, `tests`, `cli commands`) |
| `dependency_traversal` | `what depends on`, `depends upon`, `what uses`, `who uses`, `what imports`, `who consumes`, `consumers of`, `used by` |
| `reverse_dependency` | `what does X depend on`, `what do X depend on`, `what are the dependencies of X`, `dependencies of X`, `what are the imports of X`, `imports of X` |
| `impact_analysis` | `what breaks if`, `what happens if`, `impact of`, `affected by`, `what would break` + `change`/`modify`/`remove`/`refactor` |
| `data_flow` | `how does X work`, `how is X generated`, `how is X produced`, `how are X built`, `data flow for X`, `flow for X`, `walk me through X`, `pipeline for X`, `steps in X`, `explain how X` |
| `capability_check` | `does X support Y`, `can X support Y`, `capability`, `supports Y generation` |
| `status_check` | `status`, `version`, `tag`, or an `M\d+\.\d+` milestone token |
| `search` | `search <term>`, `search for <term>`, `find <term>` |
| `unknown` | no rule fires |

### Rule ordering (specificity)

1. `data_flow` rules containing `how`/`walk me through` (they contain `explain`/`does`,
   which are also entity-lookup/capability triggers — flow must win when `how` is present).
2. `reverse_dependency` (contains `depend`, which collides with `dependency_traversal`;
   the `what does ... depend on` shape must win over bare `depends on`).
3. `impact_analysis` (`what breaks if I change X` contains `what` but no `what is`).
4. `capability_check` (`does ... support`).
5. `dependency_traversal`.
6. `entity_lookup`.
7. `listing` (including the `list all <unknown-noun>` fallback → `type_filter`).
8. `status_check` (milestone-number pattern; fires only when a milestone token is present).
9. `search`.
10. `unknown`.

This ordering preserves the exact `query_type` outputs asserted by the existing test
suite (e.g. `What breaks if I change ProfileLoader?` → `impact_analysis`,
`What depends on Profile Management?` → `dependency_traversal`,
`M1.21 status` → `status_check`, `Does CareerOS support X-ray vision?` → `capability_check`,
`list all widgets` → `type_filter`).

### Data flow source

The current `_handle_data_flow_path` hard-codes the artifact-generation flow. Phase 1
generalizes it: the grammar extracts the flow topic (e.g. `artifact generation`, `cv`,
`interview preparation`) and the engine resolves it against a **deterministic flow table**
extended to cover `artifact generation`, `cv generation`, `acquisition`, `reasoning`, and
`interview preparation`. Each flow lists concrete graph nodes (labels) so related entities
and citations are produced from the graph, never invented.

## 5. Intent Classification Rules

1. **Ordered rules win by first match.** A question is classified by the first rule whose
   trigger regex matches and whose guard passes. No scoring, no ambiguity resolution.
2. **Target extraction.** The winning rule's extractor returns the target tokens using the
   existing deterministic tokenizers (`_extract_terms`, `_normalize_identifier`) plus the
   alias registry (Section 6). No NLP.
3. **Guard semantics.** If a rule's guard fails (e.g. `entity_lookup` triggered by `what
   is` but no resolvable target token), classification falls through to the next rule; if
   none passes, the question is `unknown`.
4. **Backward compatibility.** Existing behavior is preserved exactly where the test suite
   asserts it, including:
   - `What is ZzZzZzWidget?` → `entity_lookup`, answer `Could not find entity matching: ...`
   - `What depends on ZzZzZzUnknownThing?` → `dependency_traversal`, 0 entities
   - `What depends on Widget?` → `dependency_traversal`, `Nothing depends on ...`
   - `endpoints for profiles` / `cli commands` → `type_filter`
   - `Does CSKS support LLM integration?` → `capability_check` with the existing answer
5. **New intent wiring.** Two new handlers in the engine:
   - `_handle_reverse_dependency(question)`: resolve the target via `_resolve_target`
     (preferred types component/rule/generator/domain) then walk **outgoing**
     `depends_on` edges to list what the target consumes; citation per edge source.
   - `_handle_search(question)`: extract the term and delegate to the shared search
     function (Section 7) so CLI `search` and query `search` produce identical output.
6. **Milestone lookup.** `What is M1.22?` classifies as `entity_lookup`; resolution uses
   the milestone alias rule (Section 6) to find `milestone.m1.22-csks-foundation` and
   renders the Milestone rich format.

## 6. Alias Resolution Rules

`careeros/csks/aliases.py` holds a versioned, deterministic registry consulted during
entity resolution (inside `_resolve_target`).

### 6.1 Entity-type aliases

User terms → graph `type` values:

| Alias | Type |
|---|---|
| `api`, `endpoint`, `endpoints` | `api_endpoint` |
| `cli`, `command`, `commands` | `cli_command` |
| `rule`, `rules` | `rule` |
| `generator`, `generators` | `generator` |
| `schema`, `schemas` | `schema` |
| `test`, `tests` | `test` |
| `adr`, `adrs` | `adr` |
| `milestone`, `milestones` | `milestone` |
| `domain`, `domains` | `domain` |
| `component`, `components` | `component` |
| `config`, `configuration` | `configuration` |

### 6.2 Identifier normalization

Extend the existing `_normalize_identifier` convention to milestones and ADRs:

- `ADR-008` / `ADR 008` / `ADR008` / `adr.008` → `adr.008` (already shipped in M1.22.1).
- `M1.22` / `M1 22` / `M1-22` / `m1.22` → `m1.22` (milestone prefix).

Milestone resolution is a **prefix match**: a milestone node whose `tag` starts with the
normalized form (`milestone.m1.22-csks-foundation` starts with `m1.22`) resolves.
This works because milestone tags are `m{N}.{M}-{slug}` and are unique per `m{N}.{M}`.

### 6.3 Domain canonical-name registry

A curated map from user-facing canonical domain names to graph entities:

| Canonical name | Resolution |
|---|---|
| `Profile Management` | `domain.profile_management` (label match) |
| `Knowledge Layer` | `domain.knowledge_graph` (canonical label `Knowledge Graph`) |
| `Reasoning Engine` | `domain.reasoning` (canonical label `Reasoning`) |
| `Artifact Generation` | `domain.artifact_generation` (label match) |
| `Interview Intelligence` | **cluster rule**: components whose `module` starts with `careeros.interview_simulation`; deterministic set. If empty, honest ABSENT answer listing the nearest domains (`Reasoning`, `Delivery Interfaces`). |

The registry is a plain data structure (list of `AliasEntry(alias, canonical_name,
entity_id | cluster_rule | absent_hint)`), resolved in exact order. All lookups are
case-insensitive with punctuation folded.

### 6.4 Resolution precedence

For a given question, target resolution tries, in order:

1. Exact graph label match (current behavior).
2. Exact graph id / id-suffix match (current behavior).
3. Normalized identifier match (`_normalize_identifier`, current behavior).
4. Alias-registry direct match (canonical name → entity id).
5. Alias-registry cluster rule (deterministic module-prefix set).
6. Milestone/ADR tag-prefix match.
7. Absent → `Could not find entity matching: ...` / honest absent answer.

## 7. Search Behaviour

### 7.1 CLI

`careeros csks search <term>` gains a positional `term` argument (extending the existing
`--type`/`--domain`/`--limit` options, which keep working unchanged). When `term` is
provided the command prints **grouped** results:

```
Search results for "profile"
Domains:
  - Profile Management (domain.profile_management) — docs/architecture/02-domain-map.md:15
Components:
  - ProfileLoader (component.careeros.profile_loader.ProfileLoader) — careeros/profile_loader.py:16
APIs:
  - GET /profiles (api.get.profiles) — ...
...
```

Groups (only non-empty groups are printed): **Domains, Components, APIs, Schemas, Rules,
Generators, Tests, Milestones, ADRs, CLI commands, Configurations, Documents**.

Each row shows: **type, canonical name (label), location (`file:line`), short description**
(label plus, when available, a one-line purpose from source enrichment — Section 8.3).

### 7.2 Matching

Deterministic term match against `id` and `label` (case-insensitive):

1. Tokenize the term (`_extract_terms` semantics).
2. A node matches when **all** tokens appear as substrings in `id`/`label`.
3. Rank within a group: exact match > prefix match > substring match; ties broken by
   label length (shorter first) then label alphabetically.
4. Per-group cap (default 10) and global cap (default 100); both configurable.

No stemming, no embeddings, no fuzzy distance.

### 7.3 Query intent

`csks query "Search profile."` classifies as `search` and returns the same grouped text
inside `answer`, with citations for every matched entity.

### 7.4 API parity

`GET /csks/search` gains an optional `q` parameter (term search). When `q` is present the
response is:

```json
{
  "groups": {
    "Domains": [ {"id": "...", "type": "domain", "label": "...", "location": "file:line"} ],
    ...
  },
  "total": 42
}
```

When `q` is absent the existing `{ "results": [...], "count": N }` response is returned
unchanged (backward compatible).

## 8. Output Formats

### 8.1 Rich entity answers

`careeros/csks/rich_format.py` renders Components, Domains, ADRs, and Milestones as
sectioned text. Sections are emitted **only when populated**. Every section cites the
source nodes it derives from.

**Component:**

```
ProfileLoader (component.careeros.profile_loader.ProfileLoader)
  Type: class
  Module: careeros.profile_loader
  Purpose: <docstring enrichment, else fallback to structured facts>
  Responsibilities:
    - __init__
    - load
    - _parse_payload
  Public API:
    - load (method) [careeros/profile_loader.py:NN]
  Depends on:
    - <outgoing depends_on targets>
  Used by:
    - <incoming depends_on sources>
  Tests:
    - <incoming edges from dependency.tests.* nodes>
  Related ADRs:
    - <edges of type references/contains linking ADRs, if any>
  Related milestones:
    - <milestones referencing the module, if any>
  Source: careeros/profile_loader.py:16-62
```

**Domain:**

```
Profile Management (domain.profile_management)
  Purpose: <docstring/heading enrichment from docs/architecture/02-domain-map.md>
  Owned components: <components whose module maps to the domain>
  Depends on: <outgoing depends_on>
  Used by: <incoming depends_on>
  Source: docs/architecture/02-domain-map.md:15
```

**ADR:**

```
ADR-008 (adr.008)
  Title: CareerOS Self-Knowledge System (CSKS) Foundation
  Status: Accepted
  Number: 8
  Source: docs/adr/ADR-008-CSKS-Foundation.md:1-1
```

**Milestone:**

```
M1.22 — CSKS Foundation (milestone.m1.22-csks-foundation)
  Status: completed
  Tag: m1.22-csks-foundation
  Summary: <first paragraph of the milestone tag message>
  Source: git (tag m1.22-csks-foundation)
```

### 8.2 Flow answers

`data_flow_path` answers keep the numbered-step shape (`1. Profile`, `2. Load`, ...)
that the current tests assert, extended with the new flow topics and with citations to
the graph nodes that realize each step.

### 8.3 Source enrichment (deterministic, additive)

The graph carries no docstrings, so the rich "Purpose" text is derived deterministically
from the node's `source_path` file at presentation time (read-only, cached per file):

- Python files: `ast` module reads the module/class/function docstring.
- Markdown files: first non-empty paragraph after the top-level `# ` heading.
- Fallback: if the file is missing or unparseable, the Purpose line falls back to
  structured facts (module/type/methods). This fallback keeps determinism and never
  fabricates prose.

Enrichment reads only files already referenced by a node's `source_path`; it never writes,
never re-extracts, and never mutates the graph or index.

### 8.4 JSON contract

The `AnswerFormatter.format_json` response shape is **unchanged**. The `answer` string
carries the rich formatting. Only additive changes are allowed: new `query_type` values
and the optional `q` parameter on `/csks/search`.

### 8.5 Capability/status answers

Unchanged shape and content from M1.22 (`capability_check` and `status_check` tables stay
as-is except `status_check` gains the M1.22.1 milestone entry where applicable).

## 9. CLI UX Rules

1. **Unknown queries.** `_handle_unknown` output changes from `"Unknown query type. Try:
   ..."` to:
   ```
   I could not classify your query.
   Did you mean:
     - What is <topic>?        (component/entity lookup)
     - List <type>s.           (list all domains, generators, ADRs, milestones, ...)
     - What depends on <X>?    (dependency analysis)
     - What does <X> depend on? (reverse dependency)
     - What breaks if I change <X>?  (impact analysis)
     - Search <term>.          (grouped search)
   ```
   Suggestions are generated deterministically from the grammar's example templates and,
   when the question contains recognizable tokens, filled in with those tokens.
2. **Exit codes.** `search` with no term and no filters prints a usage hint and exits 0;
   an unresolvable entity via `entity` keeps exit code 1.
3. **Consistency.** CLI and API answers share the same rich formatting (both delegate to
   the formatter); the CLI adds the `Entities found / Query time / Confidence` footer.
4. **No ANSI dependence.** Rich console output stays plain-text friendly for tests and
   logs; `--json` remains available on `query`.
